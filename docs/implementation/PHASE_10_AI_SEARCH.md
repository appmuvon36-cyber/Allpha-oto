## Implemented slice

- Public read-only endpoint: `GET /v1/search/parts?q=<query>&limit=<1..20>`.
- Uses the existing FastAPI service and existing Supabase `products` and `product_fitments` data. No new database, search service, or schema migration.
- Candidate retrieval filters to `products.status = published`; a trust guard also excludes rows whose own description or condition-grade metadata explicitly labels them draft/unverified. Fitment evidence is restricted to `product_fitments.status = verified`.
- Part-number normalization removes formatting punctuation and uppercases identifiers. It does not infer that two different identifiers are semantically interchangeable.
- Deterministic ranking prioritizes exact normalized part number, exact SKU, exact name, partial identifiers, and text-token overlap.
- Results include reasons, verified fitment rows, explicit uncertainty, and a warning that the heuristic score is not a probability. The endpoint does not assert stock or shipping validity and does not make any product/fitment publication decision.
- Empty catalog remains empty. No mock listings, prices, inventory, fitments, or user activity are generated.

## Vehicle-aware search and trusted OEM/aftermarket cross-references

- `GET /v1/search/parts` accepts optional make, model, variant and year filters. Only a row already returned by `product_fitments` with `status=verified` can earn vehicle relevance. The API reports textual score, vehicle boost, combined relevance, match status and reasons separately. Candidates without matching verified evidence remain explicitly unconfirmed; no fitment status is written.
- Additive migration `20261021033934_phase10_part_number_cross_references.sql` creates the provenance/review table in the existing Supabase database. It records OEM/aftermarket number types, cross-reference relation, source class, source name, URL, checked time, reviewer, and review status. Normalized numbers are generated by PostgreSQL and indexed. RLS allows public reads only for approved rows; pending/rejected rows are staff-only. A database trigger records mapping create/review events in the existing audit log.
- Staff API and Admin UI workflow: `/part-number-mappings` lists mappings, submits source-backed mappings as `pending_review`, then separately approves/rejects. The catalog workspace links to this screen. Supported source classes are manufacturer catalog, OEM catalog, authorized distributor catalog, TecDoc, and verified supplier catalog. The source must be checked by a reviewer; an URL by itself is not proof. Public retrieval uses approved records only and returns the source provenance alongside the candidate.
- A follow-up additive migration `20261021033000_phase10_lock_reviewed_part_number_cross_references.sql` prevents changes to OEM/aftermarket numbers, relation type, manufacturer, source type/name/URL/reference, and source check time after a mapping is approved or rejected. Fixes require a new evidence record, preserving audit history. The migration was applied to the existing production Supabase project.\n- Search endpoint is connected to the customer homepage for free-text/part-number searches, passing the selected make/model/variant and returning the enriched product shape (approved media and stock summary when those optional reads succeed). Category/condition browsing continues through the existing catalog endpoint.
- The live mapping table starts empty; no equivalences were invented or seeded. This is intentional because no trusted OEM/aftermarket cross-reference dataset was supplied. Likewise, vehicle fitment remains empty until catalog staff load and review real evidence. No schema changes or writes are made to product fitment statuses by search.
